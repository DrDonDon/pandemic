The Problem

One agent. Three codebases. Three teams.

Large enterprises — telcos, banks, insurers — run customer-facing AI agents on multiple platforms simultaneously. A single agent like "billing dispute" might live on Sierra for voice, Google Agent Studio for web flows, and Cognigy for chat.

When you update that agent, you need three teams, three separate builds, three rounds of testing. A major update costs hundreds of hours. Platform versions drift apart over time, adding complexity and technical debt.

There is no tool that lets you define an agent once and deploy it everywhere. AgentSpec is that tool.

Why it's hard

The three enterprise platforms have completely different structural models:

PlatformModelStructure
SierraMonolithicOne agent, multiple journeys inside
Google Agent StudioMicroservicesMany specialised agents that hand off to each other
CognigyHybridFlows within flows, configurable depth

A schema shaped like Sierra's topology fails on Agent Studio. A schema shaped like Cognigy's node model fails on Sierra. So AgentSpec describes what the agent does — intents, entities, flows, escalations — and each deployer handles the structural translation. Same insight as Terraform: HCL describes a database, not an RDS instance.

The Schema

Six sections. No platform assumptions.

A spec file is a YAML document with six top-level keys. The schema is capability-centric, not topology-centric — it describes what the agent does, not how any given platform would wire it up.

🗂 entities

Data the agent works with. Typed, with optional PII redaction and validation patterns.

💬 intents

What users can say. Training examples + which flow to trigger.

🔌 integrations

Named backend systems. Env-var URLs, auth type, typed operations.

🔄 flows

Conversational sequences as typed steps. collect, branch, call-integration, escalate…

🛡 fallback

Global recovery: max retries, unrecognised input behaviour, escalation queue.

⚙️ overrides

Per-platform config that doesn't belong in the canonical spec. Additive only.

entities — what data the agent works with

yaml billing-dispute.yaml 
entities:
  account_number:
    type: account-number
    redact: true          # PII masking in platform logs
    validation:
      pattern: "^\d{10}$"

  dispute_type:
    type: enum
    values:
      - value: incorrect-charge
        synonyms:
          - wrong charge
          - charge I don't recognise
          - unexpected charge
      - value: duplicate-charge
        synonyms:
          - charged twice
          - billed twice

flows — conversational sequences

yaml billing-dispute.yaml 
flows:
  dispute-intake:
    entry: false
    steps:
      - id: check-dispute-history
        type: branch
        condition: "previous_dispute_count >= 3"
        then: escalate-repeat-disputer
        else: collect-dispute-type

      - id: collect-dispute-type
        type: collect
        entity: dispute_type
        prompt: "What type of billing issue are you experiencing?"

      - id: create-dispute-record
        type: call-integration
        integration: billing-api
        operation: create-dispute

      - id: route-by-amount
        type: branch
        condition: "dispute_amount <= 150"
        then: auto-resolve
        else: escalate-high-value

Available step types

TypeWhat it does
collectAsk for an entity value from the user
confirmRead back collected data and ask for confirmation
call-integrationCall a named backend operation
branchConditional fork on any entity or API output
handoff-flowPass control to another flow, optionally with entities
escalateRoute to a human agent queue
messageSend a message with no expected reply
endClose the conversation
Deployers

One spec. Multiple targets.

A deployer reads an agentspec YAML file and generates platform-native output. Each deployer handles the structural translation — the spec stays clean.

LangChain deployer working

bash
python agentspec/deployers/render.py --platform langchain agentspec/examples/billing-dispute.yaml

Generates a runnable Python file containing:

  • Pydantic input schemas for every integration operation — Literal types for enums, ge/le bounds, proper isList typing
  • @tool functions with typed signatures, auth headers from env vars
  • System prompt assembled from flows, intents, fallback rules, and a privacy section listing all redact: true entities
  • AgentExecutor with sliding window memory, model from overrides.langchain

CrewAI deployer working

bash
python agentspec/deployers/render.py --platform crewai agentspec/examples/billing-dispute.yaml

Generates Agents with role/goal/backstory derived from flow structure, Tasks chained sequentially, and a Crew ready to kickoff(inputs={"input": user_input}).

Validator

bash
$ python agentspec/validator/validate.py agentspec/examples/billing-dispute.yaml

✓ examples/billing-dispute.yaml — valid

Two passes: JSON Schema (types, required fields) then semantic checks — all flow references resolve, exactly one entry flow, PII entities warn if not redacted, escalation steps warn if account_number not in handoff_entities.

Quickstart

Up and running in 3 steps.

1

Install dependencies

bash
pip install pyyaml jsonschema
2

Validate an example spec

bash
python agentspec/validator/validate.py agentspec/examples/billing-dispute.yaml
3

Generate a deployer target

bash
# LangChain
python agentspec/deployers/render.py --platform langchain agentspec/examples/billing-dispute.yaml

# CrewAI
python agentspec/deployers/render.py --platform crewai agentspec/examples/billing-dispute.yaml

# Output lands in agentspec/out/

Set BILLING_API_BASE_URL and BILLING_API_ACCESS_TOKEN, then the generated file runs as-is once you pip install langchain-anthropic.

Known design gaps

CX Page grouping — Dialogflow CX uses a state machine (Pages). The CX deployer will need to group consecutive collect steps into a single Page form. Deployer convention, not expressed in the schema.

CX webhook tag dispatch — CX identifies webhook handlers via FulfillmentInfo.tag. The deployer auto-generates tags as {integration-name}-{operation-name}.

Training phrase annotation — both Cognigy and CX support annotating which spans in training phrases map to which entities. Current examples are plain strings. Deferred to v1.1.
